## 1. 絶対ルール

1. 変更前に、この記録へ対象・変更前後・戻し方を記載する。
2. 1項目ずつ、読み取り先と書き込み先を同時に変更する。
3. 変更後は実機で読み取り・書き込みの両方を確認し、結果を記録する。
4. 確認が完了するまで次の項目へ進まない。
5. 旧データ・旧ストア・旧処理は、移行完了と検証が済むまで削除しない。
6. 変更前のコードとGitHubコミットを追跡可能な状態で残す。
7. 本番IndexedDB、localStorage、GitHub Actions、ショートカットに対する操作は、対象と影響を確認してから行う。
8. 新しい統合先へのデータ作成は、既存アプリの読み書き先を変更せずに行う。既存画面から参照されない限り、表示動作は従来どおりとする。

## 7. 運用管理棚と独立データの保護（重要）

運用管理棚そのものは、個々の作品レコードに紐づくデータではない。棚の表示順などは独立したlocalStorage設定で管理される。一方、棚の中に配置された管理機能の一部は、現行の作品DBや独立DBを参照している。

したがって、作品DBの統合・変更によって、運用管理棚やその配下の機能が読み取れなくなることを禁止事項とする。

### 保護対象と注意点

- 運用管理棚の表示・並び順：localStorageの `tomotaYomu_mixed_shelf_order_v1` 等。作品DB移行の対象に混ぜない。
- Atom更新：独立DB `tomotaYomuAtomDB`（entries / meta）を維持する。作者情報の参照先を切り替える場合は、Atom取込・表示の両方を検証する。
- 作者整理：現行 `tomotaYomuDB.authors` を参照する処理がある。作者マスター統合後も、同等の情報を取得できるようにする。
- 本棚管理：現行 `shelf_names` / `shelf_placement` を参照する処理がある。本棚マスターと作品の所属関係を失わない。
- 読書履歴・更新管理・検索除外・ともためも：それぞれの独立DB / localStorageキーの役割を確認し、作品DBへ安易に統合しない。

### 移行方式の追加ルール

1. 旧DB・旧ストアは、切替後も管理機能の参照が残っていないと確認できるまで保持する。
2. 既存管理機能が旧ストアを参照している間は、旧ストアを読み取り専用の互換層として残すか、機能ごとに新しい参照先へ切り替える。
3. 新DBへの統合だけを先行し、既存管理機能の参照先を放置しない。
4. 運用管理棚の各リンクについて、移行前後で起動・読み込み・更新ができることを確認する。
5. 作品データの統合と、管理機能の参照先移行は別々の作業項目として記録する。

**この項目の目的は、DBを整理した結果、日常運用に必要な管理機能が壊れる事態を防ぐこと。**

### 2026-11-11（新規登録先ルールの再整理・未分類の自動判定方式）

- ユーザー決定：新規登録先として明示選択できるのは通常棚のみ。通常棚のうち `work_add_target===true` の棚があれば、その固定 `shelf_id` を新規作品へ保存する。
- 通常棚に登録先チェックが一つもない場合は、未分類を登録先とする。未分類は独立した選択操作・保存キー・作品棚IDを持たず、通常棚にチェックがない状態から画面上のチェック表示を計算する。
- 未分類の作品レコードは `shelfId: ""`。未分類棚は空白の `shelfId` を持つ作品を計算で集めて表示する。
- 本棚管理では通常棚だけに「📥登録先」操作を表示する。未分類の行には、通常棚に登録先フラグが一つもない場合に限り、計算結果として登録先マークを表示する。未分類行から登録先を設定・解除する操作は設けない。
- 登録先設定は新規登録時のみ適用する。既存作品の更新・再取得では既存 `shelfId` をそのまま維持し、空欄も空欄のまま維持する。
- なろう・カクヨム・noteの新規登録は、いずれも新DB `shelves` の通常棚 `work_add_target` を参照する。チェックがなければ空白 `shelfId` で登録する。
- 旧localStorage `tomotaYomu_work_add_target_v1=system:unclassified` は新方式の判定に使用しない。通常棚を選択した際に旧キーを削除する既存処理は残してよい。旧キーの残存だけを理由に登録先判定を変えない。
- 複数の通常棚に登録先フラグが立つ異常状態は通常運用の前提にしない。新規登録処理は最初に見つかった対象棚を使い、本棚管理で通常棚を選択した際は選択棚だけtrueに統一する。
- 既存作品データ、読書位置、しおり、作者情報、旧DBは本変更の対象外。コード変更後の実機確認は別途行い、コード反映だけで実機動作確認済みとは扱わない。


### 2026-11-11（新DB作品数の固定判定を撤廃）

- 発端：なろう新規登録テストで新DB作品数が3,600件から3,601件になり、トップ画面に「新DB作品数が想定外です：3601件（期待：3600件）」と表示され、本棚読込が停止した。

- ユーザー確認：読み取り専用監査ページで新DB作品数3,601件、N5373FWの作品レコード存在を確認。専用読み取りページで `shelfId: ""` を確認し、未分類への新規登録が成功した。
- 対応：`index.html` から3,600件固定判定のみを削除。作品数の上限は設けず、実際に読み込んだ新DBレコードを本棚構築に使用する。既存のDB存在・version・ストア構造確認と、新DB読込失敗時に旧DBへフォールバックしない安全方針は維持。
- コード反映：commit `d9f6ebc084f2f0390a994ab83264daa997428b8b`。
- 未確認：JavaScript構文テスト、本番iPhoneでの本棚再読み込み、3,601件のカード表示。コード反映を実機確認済みとは扱わない。
- 本変更は `index.html` の読込判定のみ。IndexedDB、localStorage、作品レコード、読書位置、しおり、Shortcut連携は変更していない。
