## 1. 絶対ルール

1. 変更前に、この記録へ対象・変更前後・戻し方を記載する。
2. 1項目ずつ、読み取り先と書き込み先を同時に変更する。
3. 変更後は実機で読み取り・書き込みの両方を確認し、結果を記録する。
4. 確認が完了するまで次の項目へ進まない。
5. 旧データ・旧ストア・旧処理は、移行完了と検証が済むまで削除しない。
6. 変更前のコードとGitHubコミットを追跡可能な状態で残す。
7. 本番IndexedDB、localStorage、GitHub Actions、ショートカットに対する操作は、対象と影響を確認してから行う。
8. 新しい統合先へのデータ作成は、既存アプリの読み書き先を変更せずに行う。既存画面から参照されない限り、表示動作は従来どおりとする。

## 7. 運用管理棚と独立データの保護（重要）

運用管理棚そのものは、個々の作品レコードに紐づくデータではない。棚の表示順などは独立したlocalStorage設定で管理される。一方、棚の中に配置された管理機能の一部は、現行の作品DBや独立DBを参照している。

したがって、作品DBの統合・変更によって、運用管理棚やその配下の機能が読み取れなくなることを禁止事項とする。

### 保護対象と注意点

- 運用管理棚の表示・並び順：localStorageの `tomotaYomu_mixed_shelf_order_v1` 等。作品DB移行の対象に混ぜない。
- Atom更新：独立DB `tomotaYomuAtomDB`（entries / meta）を維持する。作者情報の参照先を切り替える場合は、Atom取込・表示の両方を検証する。
- 作者整理：現行 `tomotaYomuDB.authors` を参照する処理がある。作者マスター統合後も、同等の情報を取得できるようにする。
- 本棚管理：現行 `shelf_names` / `shelf_placement` を参照する処理がある。本棚マスターと作品の所属関係を失わない。
- 読書履歴・更新管理・検索除外・ともためも：それぞれの独立DB / localStorageキーの役割を確認し、作品DBへ安易に統合しない。

### 移行方式の追加ルール

1. 旧DB・旧ストアは、切替後も管理機能の参照が残っていないと確認できるまで保持する。
2. 既存管理機能が旧ストアを参照している間は、旧ストアを読み取り専用の互換層として残すか、機能ごとに新しい参照先へ切り替える。
3. 新DBへの統合だけを先行し、既存管理機能の参照先を放置しない。
4. 運用管理棚の各リンクについて、移行前後で起動・読み込み・更新ができることを確認する。
5. 作品データの統合と、管理機能の参照先移行は別々の作業項目として記録する。

**この項目の目的は、DBを整理した結果、日常運用に必要な管理機能が壊れる事態を防ぐこと。**

## 2026-11-22：新works本番移行の基本方針・JSON命名規則

### 1. 記録の位置づけ

### 2. 作品カードとデータ参照先の分離

- 作品カード自体（デザイン、レイアウト、基本的な操作感・表示構成）は原則変更しない。

### 3. 本番移行の基本手順（合意）

1. **移行前バックアップ**：本番移行対象のDB・Object Store・必要な関連データを調査して範囲を確定し、バックアップを取得する。バックアップの保存・復元方法も確認する。
2. **現行参照先の記録**：作品カードが現在どこから何を読み、どの処理で表示・操作しているかを記録する。現行INDEX・関係コードの変更前状態も保全する。
3. **新worksへの切替**：作品カードの外観・操作を維持し、データ参照先と必要な取得処理を新worksに合わせて切り替える。
4. **移行後の確認**：作品件数・本棚・しおり／未読・短編読了切替・検索・作者・更新表示・各サイトのカード等、実際の利用経路を確認する。
5. **一定期間の通常運用**：問題の有無を確認する。問題があれば、保全した旧状態とバックアップを使って切り戻す。
6. **旧DBの削除**：安定稼働を確認し、復元可能性と保管バックアップを再確認した後に、対象と影響を特定して別工程で実施する。

### 4. 切り戻しの前提・安全条件

- 旧DBは移行後の確認期間中、変更・削除せず保全する。
- 旧DBを残したまま参照先を切り替えられる構成にできるか、実装前の現行DB調査で確認する。
- 参照先の切替だけで戻せるのは、旧DBの内容・必要な関連データが変更されていない場合。移行処理で旧DBを書き換える設計にする場合は、参照先を戻すだけでは復旧できないため、バックアップ復元を含む手順が必要。

### 7. JSONファイル命名規則（合意した基本形）

iPhoneのファイル一覧で、用途ごとにまとまり、その中で日時順に並ぶことを重視する。ファイル名は短く、プログラムからも扱いやすい半角英数字を基本とする。

**基本形：** `ty_<type>_YYMMDDhhmm.json`

- `ty`：ともたよむのファイルであることを示す固定接頭辞。
- `<type>`：用途を示す短い英語。用途名を先に置くことで、名前順に用途ごとにまとまる。
- `YYMMDDhhmm`：作成日時の月・日・時・分。日本時間（JST）で記録する。
- 拡張子はJSONを示す `.json`。小文字に統一する。
- 例：`ty_move_2611221155.json`（11月22日11時55分に作成した移行用JSON）。

用途コードの例：

| type | 用途 | 例 |
|---|---|---|
| `move` | 移行用 | `ty_move_2611221155.json` |
| `list` | 棚卸し・保存領域の一覧／構造確認 | `ty_list_2611221215.json` |
| `bak` | 本番データのバックアップ | `ty_bak_2611221235.json` |
| `rst` | 復元テスト・復元検証結果 | `ty_rst_2611221300.json` |
| `works` | 作品データ | `ty_works_2611221155.json` |
| `authors` | 作者データ | `ty_authors_2611221155.json` |

- `list` は棚卸し結果・DB構成・ストア件数・保存キー等の確認用。実データ全体を復元するためのバックアップではない。
- `bak` はIndexedDBの全対象DB・ストア・レコードとlocalStorage等、定義された対象範囲の実データを保存する本番バックアップ用。
- `rst` はバックアップJSONの復元テスト・照合結果を区別するための分類。復元テスト用データ自体を本番バックアップと混同しない。
- 今回の2026-11-22棚卸しファイルは `list`、これから取得・検証する全保存領域の本番バックアップJSONは `bak` とする。

- 同じ用途のファイルは日時部分で区別する。
- iPhone等が自動付与する `(1)`・`(2)` は正本の命名ルールとして使用しない。重複保存が起きた場合は内容・日時を確認し、正本を明確にする。
- JSON内部の形式識別子・フィールド名は従来どおり英語の仕様名を維持し、ファイル名の変更とデータ形式の変更を混同しない。
- `YY` は西暦の下2桁（2026年なら `26`）。年を含めることで、年をまたいだ同名衝突を避ける。

## 2026-11-23：なろう作品の削除・復元機能「🗑️ ごみばこ」設計方針

### 目的・対象

- なろう作品に対して、通常の削除（論理削除）と、ごみばこからの完全削除（物理削除）の両方を用意する。
- 今回の対象は **なろう作品のみ**。カクヨム・noteの作品データや削除処理は変更対象にしない。
- 表示名称は **「🗑️ ごみばこ」** とする。漢字の「ゴミ箱」ではなく、ひらがな表記を採用。柔らかく親しみやすい印象を意図した名称。
- 「保留棚」は、ともたが自由に使う通常の棚であり、ごみばことは完全に別物。通常棚へ作品を移動する操作と、削除操作を混同しない。

### ごみばこの位置づけ・表示ルール【合意済み】

- ごみばこはシステム専用機能とし、ユーザーが自由に作成する通常の棚とは分離する。
- 通常の棚マスター `shelves` には登録しない方向。
- ごみばこに入った作品は、通常の本棚一覧・全作品フォルダ・未分類・各通常棚・🆙更新棚・検索結果・通常の全作品件数から除外する。
- ごみばこ内の作品は、ごみばこ専用画面だけに表示する。
- 例：通常作品3,600件、ごみばこ5件なら、通常の全作品数は3,600件。ごみばこ5件は通常件数に加算しない。
- ごみばこへ入れる操作は削除操作であり、通常棚へ移動する操作とは別の操作とする。

### 論理削除・復元のデータ案

論理削除時は新works正本DB `tomotaYomuWorksDB/works` の対象作品レコードを残し、削除状態を記録する。

- `deletedAt`：削除日時（ISO文字列案）
- `previousShelfId`：削除直前の所属棚ID
- `shelfId`：ごみばこ内では空文字 `""` とする案。現行DBで未所属を表す空欄の扱いと整合させる。
- `bookmark`、作品情報、作者情報、`siteData` 等は保持する。
- 削除前が未分類（`shelfId=""`）なら、`previousShelfId=""` を保持する。

復元時は `shelfId=previousShelfId` として元の棚へ戻し、`previousShelfId` と `deletedAt` を解除する案。削除前が未分類なら未分類へ戻す。

※上記フィールド名・保存形式は現時点の設計案。既存コードの全読み書き経路・エクスポート・バックアップとの整合性監査を完了してから実装仕様として確定する。

### ごみばこ内の操作

- **↩️ 元に戻す**：削除前の棚へ復元する。
- **完全削除**：対象作品を物理削除する。
- ごみばこ内では通常カードの「本棚を移動」「削除」「API更新」等を表示しない。
- 完全削除はごみばこ内の対象1作品だけを対象とし、初回実装で一括完全削除は設けない。
- 完全削除の前に対象を明示した確認を行い、バックアップを取得する。確認画面は二段階とする方針。

### 完全削除時の安全条件・関連データ

物理削除は、少なくとも次の条件をすべて確認できた場合に限る。

1. 対象作品の `site==="narou"` を確認。
