# なろう全作品再取得：統合仮保存DB設計

最終更新：2026-11-21
対象：APIフル版 → Atom取得 → Translator → works更新の統合作業
状態：基本設計合意。APIフル版コード・実機検証は未実施。

## 1. 目的と基本方針

このDBはAPIだけの一時保存場所ではなく、なろう全作品の再取得・照合・変換をつなぐ独立した統合作業DBとする。

- 本番DB `tomotaYomuWorksDB` は対象作品の読み取りだけに使う。
- APIとAtomは取得経路を分けるが、同じNコードの作品レコードへ集約する。
- API・Atomの生データは加工・項目分解せず保持する。
- Translatorの照合結果・変換結果は生データと分離する。
- API取得段階ではAtom・Translator・本番DB更新を実行しない。後工程の保存場所だけを先に確保する。
- 作業ごとに独立DBを作り、中断時は保持する。削除は全工程完了・バックアップ確認後、ともたの明示承認を得てから行う。
- 進捗をlocalStorageへ保存しない。

## 2. IndexedDB構成（基本案）

作業ごとに一意なDB名を付ける。例：`tomotaYomuNarouReacquire_<runId>`。
runIdの具体的な生成形式は実装時に確定する。既存作業DBを一覧から選んで再開できるようにする。

| Store | keyPath | 役割 |
|---|---|---|
| `meta` | `id` | 作業ID、開始・更新日時、対象件数、進捗、全体状態、対象スナップショット情報 |
| `works` | `ncode` | Nコードごとの統合作品レコード。API・Atom・元作品スナップショット・Translator情報を集約 |
| `batches` | `id` | API要求バッチ、API種別、要求Nコード、試行回数、応答メタ情報、生応答、結果・エラー |

API結果を作品単位に探しやすくするため、独立した `apiResults` ストアは設けず、作品ごとのAPI生データは `works` 内に置く。バッチ全体の応答と照合記録は `batches` に保持する。

## 3. worksレコードの概念構造

```js
{
  ncode: "N2750JS",          // 正規化したNコード。worksの主キー
  source: {
    workId: "n2750js",       // 本番worksの元workId
    id: "narou:n2750js",     // 本番worksの内部ID
    snapshot: { /* 本番作品レコードの読み取り時スナップショット */ }
  },
  api: {
    normal: { status: "pending", raw: null },
    r18:    { status: "not_needed", raw: null },
    selectedSource: null
  },
  atom: {
    status: "pending",
    raw: null
  },
  transfer: {
    status: "pending",
    result: null,
    errors: []
  }
}
```

- `source.snapshot` は本番作品の独自情報（内部ID、本棚、しおり、作者情報、URL等）を後工程で保護・比較するための元データ。読み取り専用で保存し、変更しない。
- `api.normal.raw` または `api.r18.raw` には、APIが返した当該作品のJSONオブジェクト全体をそのまま保存する。API項目をこちらで列挙しない。
- API照会状況は `pending` / `found` / `not_found` / `error` 等で明確に区別する。R18 APIをまだ呼ぶ必要がない場合は `not_needed` とする。
- `atom.raw` には後工程で取得した当該作品のAtom entry原本を保持する。Atom XMLの取得・解析・保存形式の最終詳細は、現行Atom直接取得処理とR18を含む実測を確認して確定する。
- `transfer` はTranslatorの状態・結果・診断専用。生データを上書きしない。
- 上記は論理構造案。日時・試行回数・エラー情報などの補助フィールドは実装時に定義する。

## 4. API照会方式

1. 本番DB `works` から `site === "narou"` の全作品を読み取る。作品区分や検索除外状態を理由に対象から除外しない。
2. Nコードを抽出・正規化し、形式不正・重複を別途集計する。
3. 対象全件の固定スナップショットを `works` に作る。
4. 全対象を通常小説APIへ照会する。
5. 通常APIが正常応答し、要求Nコードが返らなかった作品だけをR18小説APIへ照会する。
6. 通常APIの通信・HTTP・タイムアウト・形式・部分応答・照合エラーは未完了として再試行し、R18 APIへ送らない。
7. R18 APIでも正常応答したが返らない作品は「両API正常応答・対象なし」とする。削除確定ではない。
8. 要求・返却Nコード、`allcount`、返却行数、重複・未知コード・形式不正を照合する。
9. API結果と本番DB区分が食い違っても、本番作品データを自動変更しない。

API生データは作品レコードに一度だけ保存する。バッチ記録には `allcount`・要求コード一覧・応答コード一覧・試行情報・エラー情報を保存し、生データを重複保存しない。これにより、端末容量を抑えながら作品単位の参照とバッチ単位の監査を両立する。

## 5. 段階検証

- 既存の10作品実験はAPI接続・JSONP・全項目取得・生データ保存の既存実績として再利用し、同じ実験を最初から繰り返さない。
- 今回新しく実装する仮保存DB、作品単位の保存、要求・返却照合、中断・再開だけを少数件で確認する。
- 検証対象の累積範囲を10件 → 100件 → 500件 → 1,000件 → 全件へ拡大する。
- 1回のAPI要求は最大100件を初期上限とする。100件を超える連続処理・応答サイズ・時間・再開を確認する。
- 全項目取得時の応答完全性とAPI制限を実測してから、バッチサイズ・間隔・タイムアウト等を確定する。
- 完了済みNコードは再取得せず、未完了・再試行対象だけを再開する。

## 6. Atomとの統合

- Atom取得はAPI工程完了後の別工程。APIフル版の初期実装ではAtomを取得せず、同じ `works` レコード内の `atom` 領域を未取得状態で確保する。
- Atom取得時はNコードで対応する作品レコードを特定し、そのレコードへAtom原本を追加する。
- 現行 `tools/diagnostic/ncode_extract.html` には、通常API endpointに `out=atom&ncode=...` を指定してXMLを直接取得する試験処理がある。これは先頭3件の全年齢作品を使う保存なしテストであり、全件・R18を含む統合取得の完成実績とは区別する。
- `data/atom/author-feeds.json` は作者別Atomフィードの直近7日スナップショットであり、全作品のAtom原本を保持するデータ源としてそのまま流用しない。
- Atom原本の格納形式（作品別entry XML、必要に応じてバッチ全体XMLの監査保存）と、R18 Atom endpointを含む取得方法は、Atom工程開始前に現行コード・実測を確認して確定する。
- Atomの通信失敗・Nコード不一致・entry重複はAPI結果と混ぜず、Atom工程の状態として記録する。

## 7. 安全境界・削除条件

- 本番DBはreadonly。API工程では本番DBへの書き込みなし。
- 旧DB、LabDB、既存判定センター、既存Transfer Lab、localStorage、Shortcut、GitHub Actions既存設定を変更しない。
- 仮保存DBは作業中・中断中に削除しない。
- API・Atom・Translatorの全工程、照合、バックアップ、復元確認が完了した後、内容確認とともにたの明示承認を得てから削除する。
- 本番works更新は別工程。更新対象・差分・独自情報保持・バックアップ・復元方法を確認し、別途明示承認を得るまで実行しない。
