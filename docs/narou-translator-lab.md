> この資料は設計・検証の記録であり、本番登録ページや本番DBを変更する指示ではない。未確認の仕様を確定事項として扱わず、実装可能性・取得可能性・運用負荷を確認してから採用する。

## 1. 開発の目的

既存のなろう登録経路を調査・参考にしながら、なろう通常作品の取得データを、ともたよむの共通 `works` 項目へ適切に変換する「通訳レジスター」を整備する。

単に現在の登録処理を移植するのではなく、共通項目・サイト固有項目・取得できない項目を区別し、将来の保守と他サイトへの展開を考慮した理想形を追究する。

## 2. 基本方針（合意済み）

1. **入口はショートカットURL。** ショートカットから登録ページへ対象情報を渡す。
2. **通訳ページは通過点。** 取得・変換・登録に必要な処理を行うが、作品データを永続保存しない。
3. **出口は `works` のみ。** 変換後の作品レコードを作品DBの `works` へ登録する。通訳ページや別の中間保存先を作品情報の正本・参照先にしない。
4. **変換ルールはサイト別に明確化する。** なろう固有の取得形式・値を確認し、共通項目へ変換する。無理な共通化はしない。
5. **実験は本番から隔離する。** 実験用ページ `narou_transfer_lab.html` と独立したLabDBを使い、本番DB・本番localStorage・現行Shortcutの実データ経路を変更しない。
6. **現行本番ページは保護する。** 既存 `register.html` は現行登録経路として残し、調査・参照対象とする。実験中は変更しない。
7. **実現可能性を先に確かめる。** API取得可否、データの有無、変換方法、実行環境、処理負荷を確認し、実行できない要件を積み上げない。
8. **本番導入時に名称を整理する。** `_lab` は開発・実験中の識別子。本番導入時は外す想定だが、最終ファイル名・配置・Shortcut URLの切替は完成後に判断する。

## 11. 2026-11-17：Transfer／Translatorの共通works変換方針

### 11-1. 全体のデータ経路（仕様方針）

```text
WEBサイト
  ↓ URLを共有
iOSショートカット（URLを受け取る）
  ↓ 対象URLを渡す
サイト別Translator（取得・項目名統一・形式変換・整理）
  ↓ 共通works形式のレコード
works（作品情報の正本）
  ↓ 読み取り・参照
作品カード
```

- **Transfer**：各サイトの作品データを、ともたよむ共通形式へ受け渡す一連の仕組み。
- **Translator**：サイト固有のAPI・データ項目を読み取り、意味が同じ情報は共通works項目へ変換・整理するサイト別処理。
- **Register**：変換済みデータを本棚へ登録する最終処理。今回の実験室には持ち込まず、Translator／Transferの実験対象から分離する。実際の本番接続・登録経路は別途検証する。
- **works**：作品情報の正本。サイト別の違いをTranslatorで吸収し、作品カードは共通works項目を参照する。
- なろう用のTranslatorに続き、将来はカクヨム・note等もサイト別Translatorを用意し、共通worksへ渡す構想。

#### キーワードの変換（2026-11-17 仕様確定）

- 全年齢API・R18 APIの `keyword` を共通worksの `keywords` に取り込む。
- APIの `keyword` は空白区切りの文字列であるため、空白で分割して文字列配列に変換する。
- 例：`"異世界転生 白い結婚 美貌の公爵家"` → `["異世界転生", "白い結婚", "美貌の公爵家"]`
- API側の項目名 `keyword` と、共通works側の項目名 `keywords` を区別する。
- `keyword` が空文字・null・空白のみの場合は、キーワード内容なしとして扱う（空の文字列をキーワード要素として登録しない）。
- 既存作品の更新時に `keyword` が空文字・null・空白のみの場合は、既存の `keywords` を上書きせず、そのまま保持する。
- 区切り文字が空白以外で現れた場合の扱いは、実データで確認して別途定義する。

#### statusの判定

| `novel_type` | `end` | 共通worksの `status` |
|---:|---:|---|
| 2（短編） | 0 | `短編` |
| 1（連載形式） | 0 | `完結` |
| 1（連載形式） | 1 | `連載中` |

全年齢API・R18 APIで同じ条件を使用する。想定外の値・組み合わせは誤判定せず、調査対象として扱う。

#### genresの共通構造（配列形式の方針確定）

共通worksには、ジャンルと属性をまとめる単一の `genres` 配列を設ける。目的は、将来必要になったときに元情報を取り出しやすくしておくこと。現段階では表示名への変換や画面表示を行わない。

- 全年齢APIの `biggenre`・`genre`、R18 APIの `nocgenre` を同じ `genres` 配列に格納する。
- BL・GL・残酷描写・異世界転生・異世界転移等の属性フラグ、および `isr15` も同じ配列に格納する。
- 各要素は元API項目名（`source`）と元の値（`value`）を組にして保持する。値を独自に `true` / `false` へ変換せず、APIから受け取った値・型を保つ。
- 表示名への変換、ジャンル辞書、属性の表示処理は今回の対象外。取り出しやすく、元情報を失わない保存を優先する。

### 11-4. API項目の採否

#### 取り込まないことを確認済み

| API項目 | 扱い | 理由 |
|---|---|---|
| ポイント・評価・ブックマーク数・感想数・レビュー数等 | 取り込まない | ともたが不要と判断 |

#### APIに存在することを確認済みの項目と採否

| API項目 | 確認内容 | 採否・扱い |
|---|---|---|
| `keyword` | 全年齢・R18の両APIに存在 | **仕様確定：共通worksの `keywords` に文字列配列として取り込む** |
| `biggenre`・`genre` | 全年齢APIに存在 | **方針確定：共通worksの単一 `genres` 配列に、元項目を識別できる形で格納する** |
| `nocgenre` | R18 APIに存在 | **方針確定：共通worksの単一 `genres` 配列に、元項目を識別できる形で格納する** |
| `length` | 両APIに存在 | **方針確定：共通worksに取り込まない（単なる文字数であり、現時点で利用目的がないため）** |
| `time` | 両APIに存在 | **方針確定：共通worksに取り込まない（利用目的がないため）** |
| `novelupdated_at` | 両APIに存在 | **方針確定：取り込まない。共通worksの日付は `publishedAt` と `lastPublishedAt` の2項目に限定する** |
| `updated_at` | 両APIに存在 | **方針確定：取り込まない。共通worksの日付は `publishedAt` と `lastPublishedAt` の2項目に限定する** |
| `isstop` | 両APIに存在 | **取り込まない**（更新停止情報は不要） |
| `gensaku` | 両APIに存在 | **取り込まない**（原作情報は不要） |
| `kaiwaritu` | 両APIに存在 | **取り込まない**（会話率は不要） |
| `sasie_cnt` | 両APIに存在 | **取り込まない**（挿絵数は不要） |

### 11-5. API情報とともたよむ独自情報の更新権限

- サイト由来の作品情報（作品名・あらすじ・作者名・話数・ジャンル・掲載日等）は、APIを正として更新する。
- ともたよむ独自情報（内部 `id`、本棚 `shelfId`、しおり `bookmark`、検索除外等）はAPIで上書きしない。
- R18の手動登録作者IDや、作者かな等の手動・別経路情報も、APIに項目がないことを理由に消さない。
- R18 APIから作者ID（`userid`・`XID`）を取得できない作品は、`authorName` を保存し、`authorId` は未設定のまま作品データを取り込めるようにする。作品登録を作者IDの取得待ちにしない。
- `authorId` は初回登録時に通常APIの `userid` を設定する。R18作品は作者登録機能で後から手動登録・紐付けする。いったん値が設定された `authorId` は、通常のAPI更新で変更・削除しない。作者名だけから作者IDを推測・生成しない。
- `authorKana`・`authorKanaFirst`・`authorKanaChecked` は、既存レコードに記録があればそのまま維持する。Translatorへこれらのデータが渡された場合は取り込む。新たな自動取得機能は追加しない。
- APIに項目自体がない場合は既存値を維持する。
- API項目が空文字・null・空白のみの場合は、その項目を上書きしない。既存値があれば維持し、既存値もなければ未設定のままとする。意図的な削除はAPIの空値とは別の操作として扱う。
- `id` はともたよむ専用。APIから取り込まず、既存作品の更新時にも変更しない。
- 作者名と作者IDは別々に扱う。R18 APIに作者IDがない場合、作者名からIDを推測・生成しない。

### 11-6. API取り込み設計の仕上げチェック

| 項目 | 確定内容・残作業 |
|---|---|
| `keyword` → `keywords` | 空白区切りを文字列配列へ変換。空文字・null・空白のみは内容なしとし、既存作品では既存値を維持 |
| `biggenre`・`genre`・`nocgenre` | 単一の `genres` 配列へ格納し、元項目名と元の値を保持 |
| 属性フラグ・`isr15` | `genres` 配列へ元項目名と元の値を保持。0/1をBooleanへ変換しない |
| `length`・`time` | 取り込まない |
| `novelupdated_at`・`updated_at` | 取り込まない。日付は `publishedAt`・`lastPublishedAt` の2項目 |
| `isstop`・`gensaku`・`kaiwaritu`・`sasie_cnt` | 取り込まない |
| `authorId` | 初回取得時に通常APIの `userid` を使用。R18はAPIに項目がないため未設定で取り込み可。いったん登録した作者IDは通常のAPI更新で変更・削除しない |

### 11-7. Lab段階の安全境界

- 本番DB・本番localStorage・現行Shortcut・GitHub Actions・本番登録ページは変更しない。
- LabDBで項目対応・変換結果・既存独自情報の維持を検証する。
- 変換ルールと項目対応表はこの資料を正本として更新する。
- なろうTranslatorページ自体にも「何のデータを、何に変換するページか」を常設表示する。ページ説明・変換対応表・除外項目・更新履歴を残し、実装と資料が食い違わないようにする。
- カクヨム・note等の他サイトのデータを、なろうAPIの検証データに混ぜない。
- 警告棚構想は判定センターとの共同開発候補として別管理し、今回のTranslator項目対応表・Lab実験には混ぜない。
