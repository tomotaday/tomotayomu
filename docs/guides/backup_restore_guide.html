💾 バックアップ・復元ガイド

保存領域のバックアップ機能、2026/11/08時点の復元・表示検証結果、および今後の保全方針を記録する。

初回バックアップ・復元検証｜2026/11/08

バックアップJSONの書き出しに成功し、Safari上に専用の検証用IndexedDBを作成して、5ストア・9,850件の復元後データが元データと完全一致することを確認した。さらに、検証用DBを読み取り専用で開き、本棚表示まで確認した。

この確認はバックアップ機能の初回デビューを示すもの。アプリ全体の完全復旧を保証するものではない。

4. Safariでの本棚表示検証

復元済みの専用DBを、restore_render_test.html から読み取り専用で開き、なろう作品を棚ごとに表示した。検索機能も含め、検証用データの表示を確認した。

  • 読み取り専用トランザクションで5ストアを参照する。
  • 本番DB名 tomotaYomuDB は開かない。
  • localStorageを参照・変更しない。
  • 表示確認ページからレコードの追加・更新・削除を行わない。
  • 読み込み後にDB接続を閉じる。

Brave本番とSafari検証の件数差

画面比較では、Brave本番の作品数がSafari検証より4件多かった。差分はカクヨム・note作品の合計4件（📌に3件、未分類に1件）であり、Safari側の表示試験はなろうIndexedDBの5ストアを対象としているため、この4件は表示対象外。なろう作品の棚別件数は、差分を除けば一致した。

したがって、この4件の差は今回の検証対象の違いによるもので、なろう作品データの欠落を示すものではない。

5. しおり・作品情報の確認で分かったこと

  • 複数作品の画面比較では、読み進めた話数の分子がBraveとSafariで一致する例を確認した。ただし、サンプル数が限られるため、全作品での一致を断定しない。
  • Nコード N2215GH の作品では、IndexedDBの works_cache に最終更新日 2026-10-25 04:00:00・全410話が保存されていた。
  • 同じ作品のlocalStorageキー tomotaYomu_v214_latest_works には、最終更新日 2026-11-08 00:00:00・全411話の情報が保存されていた。
  • Safari検証ページが表示した410話はIndexedDBのバックアップ内容と一致しており、Brave本番側の411話はlocalStorage側の新しい情報による表示と確認できた。
重要な発見：作品メタデータが2か所に存在する

works_cache と localStorage の tomotaYomu_v214_latest_works に、同じ作品のメタデータが保存されている。後者にはIndexedDBより新しい情報が含まれる場合があり、現行画面では新しい情報を上書き表示する役割を持つ。

このため、localStorage側のデータを単純に削除したり、二重保存をすぐに解消したりすると、更新済み情報が古い内容に戻る可能性がある。

6. 今後の保存領域の検討課題

保存先を一つに整理する設計は候補となるが、現時点では方針決定・移行を行わない。まず両方の保存内容と利用箇所を調べる。

  1. latestWorks の全件数と各レコードを確認し、works_cache と比較する。
  2. どちらが新しいかを判断する条件（更新日時、情報の完全性など）を決める。
  3. 移行する場合は、更新情報の取りこぼしや巻き戻りがないことを照合する。
  4. 作品更新・候補取得・画面復元などの処理が、どの保存先を使っているか監査する。
  5. 新方式で複数回の検証を行い、旧キーを廃止できると確認できるまで保持する。

現時点では二重保存の理由・全ライフサイクルを調査しきっていない。二重保存が不要と確定したわけではなく、統合は設計上の検討候補である。

7. 安全方針・未実施事項

現状維持を優先する
  • Brave本番のIndexedDB・localStorageを、この検証のために消去・初期化しない。
  • Safariに既に存在していたDBも、ユーザーの明示指示なしに削除・初期化しない。
  • Safariに作成した検証用DB tomotaYomu_restore_test_20261108084247875 は残してある。明示指示なしに削除しない。
  • 本番の index.html を復元テストのためにSafariで直接実行しない。
  • バックアップ機能と保存領域の設計変更は別作業として扱う。
  • 本番データ、IndexedDB、GitHub Actions、ショートカット連携を壊さない。変更は小さく分けて検証する。

まだ確認していないこと

  • 4つのIndexedDBすべてを新しい環境へ復元し、アプリ全体を復旧できるか。
  • localStorageを含む全保存領域の復元と、本体アプリでの整合性。
  • Safariで最初に発生した「One of the specified object stores was not found.」の原因確定。
  • Safariの復元テストページが、時間経過後に再表示時エラーとなった原因確定。
  • しおりの話数・総話数の差が、全作品でどのような条件で発生するか。
  • latestWorks と works_cache の二重保存の全体像と統合可否。

8. 現時点での結論

バックアップJSONの書き出しと、主要な本棚DB（tomotaYomuDB）の復元・全件照合・読み取り専用表示は実機で確認できた。よって、バックアップ機能は初回デビューを果たした。

一方で、今回の試験はアプリ全体の完全復旧試験ではない。また、作品メタデータがIndexedDBとlocalStorageに二重保存され、localStorage側に新しい情報が存在することが分かった。

当面はバックアップ機能を現状維持し、保存領域の構造は慎重に調査・検討する。確認が終わる前にデータ移行・削除を行わない。
